## Finding 1: Overdue digest is dead on arrival — the ceiling is below the day-one population and there is no drain path
- **Severity:** Critical
- **Location:** Phase 4, "Implementation Steps" step 8; "Requirements" 2, 9; "Architecture" (ceiling check → "send NOTHING")
- **Flaw:** The default ceiling is 500 emails and the rule on breach is "log, operator summary, send **no** learner mail, exit 0". The mirror has 843 distinct learners with open overdue rows today. The ceiling is a single check over the whole run, so it also starves the T-3 stage. Nothing is stamped on a refused run, so tomorrow's input is the same 843 plus whatever went overdue overnight (195 more assignments fall due within 10 days). The job refuses forever.
- **Failure scenario:** Switch flipped after copy sign-off → day 1: 843 digests + N reminders > 500 → nothing sent, exit 0, green in CloudWatch. Day 2..∞: identical. The 53%-overdue problem the phase is sequenced by is untouched, and the "exit 0" makes it look healthy. Raising the ceiling to 1,000 instead sends ~843 emails in one Lambda invocation (see Finding 2).
- **Evidence:** phase-04 step 8: "The ceiling (`ASSIGNMENT_REMINDER_MAX_EMAILS`, default 500) … Over the ceiling: log, send the operator a summary … send **no** learner mail, exit 0." Mirror: `db.groupassignments.distinct('user', {dueDate:{$lt:now}, status:{$in:['active','in_progress']}, deletedAt:null}).length` → 843. Requirement 2 also says the digest lists "*all* their past-due open assignments" while query B filters `overdueDigestSentAt: null` — a learner who already received one digest gets a second listing only the newly-overdue row, and never another for the original seven.
- **Suggested fix:** Separate ceilings per stage so overdue backlog cannot starve T-3. Replace refuse-all with **drain**: send the oldest-due N per run, stamp them, carry the rest to tomorrow, and log `remaining`. Define digest cadence explicitly (e.g. weekly per learner while any row is open) with the idempotency key at `(user, stage, dateKey)` grain rather than per row — see Finding 2.

## Finding 2: Reminder Lambda inherits the 28 s provider timeout; send-then-stamp under a timeout produces duplicate emails on the next cron
- **Severity:** High
- **Location:** Phase 4, "Related Code Files → Modify → serverless.yml"; step 8 ("Order: connect → query → filter → ceiling → send → stamp"); Risk table row "Duplicate sends on a retried invocation"
- **Flaw:** The new function block is specified as `cron(0 13 * * ? *)`, `enabled: false` — no `timeout`, `memorySize`, or `reservedConcurrency`. `provider.timeout: 28` applies (`serverless.yml:16`); every existing worker overrides it (`:54`, `:80`, `:93`, `:109`). `sendEmail` is not cheap per call: two `secrets.get` round-trips and an `eta.renderAsync('note')` before the provider HTTPS call (`src/lib/mail/index.ts:135-142`). Several hundred sequential sends will not finish in 28 s. The plan's mitigation for duplicates is `maximumRetryAttempts: 0` — that prevents Lambda's *error* retry, not the daily *schedule* re-invoking over rows that were sent but never stamped because the process was killed.
- **Failure scenario:** Run sends 300 emails in 28 s, Lambda is terminated, 0 or 300 rows stamped depending on batching; tomorrow the same 300 learners get the same reminder. Repeats daily until the backlog fits in 28 s. With no `reservedConcurrency: 1`, a manual test invoke overlapping the cron doubles sends within the same minute.
- **Evidence:** `serverless.yml:16` `timeout: 28`; `:107-118` the cited precedent sets `timeout: 300`, `reservedConcurrency: 1`, `maximumRetryAttempts: 0`. Plan risk row: "a stamp alone loses to a crash between send and update" — acknowledged, then mitigated with the wrong control. `src/lib/mail/index.ts:135-142`.
- **Suggested fix:** Copy the precedent block verbatim (`timeout: 600`, `memorySize: 512`, `reservedConcurrency: 1`). Invert to **claim-then-send**: `findOneAndUpdate({_id, reminderSentAt: null}, {$set:{reminderSentAt: now}})` per row/user *before* the send, and `$unset` on a `null` result from `sendEmail`. At-most-once is the right default for email. Check `context.getRemainingTimeInMillis()` between sends and stop cleanly with a `remaining` count.

## Finding 3: Phase 8's "one shared row builder" and "never a per-member loop" are mutually exclusive; the 1,000-member ceiling bounds nothing real
- **Severity:** High
- **Location:** Phase 8, "Architecture → Why a new leader route rather than reusing the export"; steps 2 and 4; Risk row "N+1 on a large group"
- **Flaw:** Step 2 says extract the existing export's assembly into `course-progress-report.helper.ts` as "a pure refactor with no behaviour change". That assembly *is* the N+1: `for (const group of groups)` → `getCoursesByGroupId` → `getGroupMembersByGroupId` → `for (const course of courses)` → `for (const member of members)` → `userCourseProgressService.getUserProgressByCourseId(user.id, course.id)` per member (`manager.controller.ts:836-880`). Step 4 then says "never a per-member loop". Both cannot be true of one function. The report route runs inside the `api` Lambda with `timeout: 28` (`serverless.yml:16`) and API Gateway's 30 s hard cap. The largest real group is 719 active members; the proposed ceiling is 1,000, so it never fires and the timeout is the actual bound.
- **Failure scenario:** Leader of the 719-member group opens the Progress tab: 719 × 2 courses = 1,438 sequential Mongoose finds hydrating ~29 KB average documents (mirror `avgObjSize`) with `items[]` up to 185 entries → API Gateway 503/504 at 30 s, React Query retries per `shouldRetryApiError`, leader sees an error state and the sweep row (`/administer/groups/6a6ae3d7…/progress`, 201 members) may pass while production groups fail.
- **Evidence:** `manager.controller.ts:836-880` (loops shown above); `serverless.yml:16`; mirror: `groupmembers` active counts 719 / 433 / 350; sweep group 201 active members, 2 courses.
- **Suggested fix:** Write the batched builder first (one `groupmembers` read, one `usercourseprogresses.find({user:{$in}, course}).select('user progress status completedItems totalItems lastAccessedAt').lean()`, one `groupassignments` aggregation), then make the export call **it** and prove workbook equality with a before/after fixture — accept that this is a behaviour-preserving *rewrite*, not a "pure refactor". Set the ceiling from a measured p95 under 28 s, not a round number; require `courseId` above it.

## Finding 4: Position `updateOne` races `/track`'s transaction; the 80 % completion POST can abort and is then silently dropped by the client
- **Severity:** High
- **Location:** Phase 2, "Architecture → Why a separate route"; Requirement 8; steps 3, 9, 11; Risk row "`arrayFilters`/positional `$` selects the wrong item"
- **Flaw:** Traced path for `/track`: `learners.controller.ts:355` `startTransaction` → `:357` read progress doc inside the session → `processTopicProgress` mutates in memory → `learners.process.topic.ts:247` `save({session})` → commit. A non-transactional position `updateOne` that commits between the snapshot read and `save()` raises a WriteConflict on the transaction; the controller retries 3× with 100/200 ms backoff (`:350`, `:530-537`) then throws. Two things make the collision systematic rather than incidental: (a) the throttle "true when never written" fires a position PUT on the first `timeupdate`, racing the mount ping's transaction (`use-track-course-item-view.ts:67-74`); (b) the 80 % `trackNow` and the throttle both consume the same `timeupdate` stream. On the client, `trackNow` is `void`ed (`topic-view.tsx:46`) and the plan adds `hasFiredRef` so the threshold "fires ONCE per mount" — a failed completion POST is never retried. Separately, the plan's "no whole-document rewrite" framing is incomplete: when one `save()` both `$push`es a new topic item and `$set`s a field on an existing item (parent lesson `lastAccessedAt`, `process.topic.ts:35-45`, on every first visit to a topic in an already-started lesson), Mongoose cannot combine `$push` and `$set` on the same array path and `$set`s the entire `items[]` — exactly the 185-entry rewrite Requirement 8 says the new route avoids.
- **Failure scenario:** Learner crosses 80 % at t=612 s; the same tick also satisfies "≥12 s since last write". PUT lands first; POST's transaction aborts ×3 → 500 → swallowed by `void trackNow(...)`; `hasFiredRef` is set; the outline still says `in_progress`. This is the regression the phase exists to remove, now intermittent and invisible.
- **Evidence:** `learners.controller.ts:350-357, 526-540`; `learners.process.topic.ts:35-45, 227-247`; `topic-view.tsx:45-47`; `use-track-course-item-view.ts:67-74`; phase-02 step 9 "fires ONCE per mount … Guard with a `hasFiredRef`", step 10 "true when never written".
- **Suggested fix:** Client: do not `void` the completion POST — await it, reset `hasFiredRef` on failure and re-arm on the next `timeupdate`; suppress position writes for ~2 s around any `trackNow`; do not write position before the mount ping resolves (the plan already assumes it "always lands first" — make it true). Server: add a functional test that runs a position PUT concurrently with a `/track` and asserts the POST still completes (retry count or a short `maxTimeMS`). Document the whole-array `$set` case honestly in Requirement 8.

## Finding 5: "Final write on unmount" does not fire on the exit path the plan is designed around (tab close), and nothing in the stack uses `keepalive`
- **Severity:** Medium
- **Location:** Phase 2, Requirement 3; step 10; Risk row "Vimeo `timeupdate` stops firing on a background tab"
- **Flaw:** React does not unmount on `beforeunload`/tab close, and a `fetch` issued from an unmount cleanup during navigation away from the SPA is cancellable by the browser without `keepalive: true` or `sendBeacon`. Neither exists in `packages/api-client/src` or `apps/web/src` (grep: zero hits). The existing unmount ping has the same weakness (`use-track-course-item-view.ts:76-83`), so the plan inherits a known-lossy pattern and then claims "the last known position is never more than one tick stale".
- **Failure scenario:** The plan's own persona — "watches 97 % of a lecture and clicks away" — closes the tab: last write was up to 12 s ago (or 15 s of seek), no pause event, no unmount. Resume lands 12 s early. Tolerable alone; combined with Finding 4 it means the only completion signal *and* the last position can both be lost at the same moment.
- **Evidence:** `use-track-course-item-view.ts:76-83` ("Fire-and-forget: nothing can await a promise from inside an unmount cleanup"); grep `keepalive|sendBeacon` → none; phase-02 risk table row cited.
- **Suggested fix:** Add a `pagehide`/`visibilitychange→hidden` listener in the hook that issues the final position write with `fetch(..., { keepalive: true })`; expose a `keepalive` option on the api-client request layer. Change the risk row to say what is actually guaranteed.

## Finding 6: Persistent shell resumes from a stale outline position; `?tab=` back-button claim contradicts the repo's own `nuqs` usage
- **Severity:** Medium
- **Location:** Phase 5, Requirement 8 ("fetched once per course visit"), step 8 (resume from `item.positionSeconds`), Requirement 7 (`?tab=` + back button); Phase 2 step 11 (position writes do not invalidate the outline)
- **Flaw:** Three decisions combine badly: the outline is fetched once per course visit and never remounts; position writes deliberately do not invalidate it; the player resumes from the outline's `positionSeconds`. The only refetch is the mount ping's `invalidateOutline()` (`use-track-course-item-view.ts:73`) on entering the *next* item, which races the previous item's fire-and-forget unmount PUT. `QueryClient` default `staleTime: 30_000` (`apps/web/src/app/query-client.ts:16`) means even a remount would not refetch within 30 s. The resume pointer itself is `lastItemAccessed` (`learners.outline.helper.ts:270-277`), which the position write sets — that part is coherent.
- **Failure scenario:** Watch A to 12:00 → click B (A's unmount PUT in flight; B's mount POST → invalidate → GET outline returns A at 11:36 because the PUT had not committed) → click A → `PlayerFrame key=A` remounts and `setCurrentTime(696)`. Every in-shell round trip resumes behind. The plan's manual step 4 only tests *reload*, which refetches and hides this.
- **Evidence:** phase-05 Requirement 8, step 8, manual pass step 4; phase-02 step 11 "does **not** invalidate the outline"; `query-client.ts:16`; `use-course-outline.ts` sets no `staleTime`; `use-list-url-state.ts:54-56` uses `{ replace: true }` and the plan cites that file as the `nuqs` precedent while asserting "the browser back button works".
- **Suggested fix:** On each position write resolution, `queryClient.setQueryData(courseKeys.outline(courseId), patchItemPosition(itemId, seconds))` — no refetch, no 185-item round trip, and the shell reads the fresh value. Or hold `positionByItemId` in shell context and let `PlayerFrame` prefer it. Specify `history: 'push'` for the tab param explicitly and add a manual step for in-shell A→B→A resume.

## Finding 7: Backfill idempotency leaves permanent stale rows; the "mismatch treated as absent" guard cannot be implemented where the plan puts it; empty local token does not fail loudly
- **Severity:** Medium
- **Location:** Phase 1, Requirement 6; Risk row "Sidecar drifts when a topic's embed is re-authored"; "Security Considerations" (empty-string fallback "fails loudly"); "Related Code Files → Create" (test precedent)
- **Flaw:** (a) Requirement 6 says a re-run "changes only `fetchedAt`" — so a topic whose embed was removed keeps its `v2topicmedia` row and duration forever. (b) The mitigation is "Phase 3 treats a row whose `vimeoVideoId` no longer matches the live content as absent" — but `fetchOutlineContent` selects only `_id title status` (`learners.outlinecontent.helper.ts:63`); honouring that rule at read time means loading up to 185 HTML bodies per outline request, or the rule silently is not implemented. (c) `secrets.get` throws only on `undefined`/`null` (`src/lib/secrets.ts:290-294`); an empty-string `LOCAL_DEV_SECRETS` entry is returned as `''`, so a tokenless local run sends `Authorization: Bearer ` for 465 videos and *succeeds* in writing 869 `fetchError` rows — a valid-looking 0 % coverage report. (d) The cited test precedent `tests/scripts/migrate-repair-progress-status.test.ts` does not exist; `tests/scripts/migrate-repair-demoted-progress.test.ts` does.
- **Failure scenario:** Content team swaps a video in a topic (new id) — row's `vimeoVideoId` differs, outline still shows the old duration; or a video is *replaced in place* on Vimeo (same id, new length) — duration stale with no signal at all, since nothing schedules a re-run. Phase 6's caption gate could be computed from a run that never authenticated.
- **Evidence:** `learners.outlinecontent.helper.ts:58-68`; `src/lib/secrets.ts:286-316`; `ls tests/scripts/` → `migrate-repair-demoted-progress.test.ts` only; phase-01 Requirement 6, risk row and security bullet as quoted.
- **Suggested fix:** Do the mismatch check in the backfill (it already has the HTML): null out or delete rows whose topic no longer embeds, store `contentEmbedIds[]` on the row so Phase 3 can compare cheaply if ever needed. Treat `''` token as fatal before the first request, and make the report refuse to write if `failed === asked`. Schedule the backfill (monthly EventBridge or on console topic save) or document that durations are a snapshot. Fix the citation.

## Finding 8: The forward-only "proof" runs over 10 documents, and the phase does not state that the 731 stalled 75–99 % learners are not flipped
- **Severity:** Medium
- **Location:** Phase 2, "Regression gate" item 7; "Success Criteria" bullet 3; Risk row "A completed item is downgraded"
- **Flaw:** Gate 7 is a before/after count of completed items on the mirror after "a full browser pass". The mirror holds 10 `usercourseprogresses` (184 completed items); a browser pass that completes anything makes the count rise regardless of whether a downgrade path exists. It is presented as "proven … not by inspection". The actual guarantee is in code and does hold on trace: `wasCompleted` short-circuit (`learners.process.topic.ts:193-197`) covers `/track`, and the position route by construction never writes `status`. But the plan also implies the phase fixes "in progress forever": detection is client-side at playback time only, so an item left `in_progress` under the old `ended` rule (a learner who watched 85 %) stays `in_progress` until they replay past 80 % in a new session. No backfill, no retroactive flip — correct, but unstated, and it changes what the Phase 3 "Continue" row shows to the 731.
- **Failure scenario:** Gate 7 passes on 10 docs; a later refactor of `determineTopicStatus` (Phase 6/8 touch the same helper family) introduces a downgrade; the same gate still passes. Meanwhile stakeholders read Success Criterion 1 as applying to existing stalled learners and it does not.
- **Evidence:** mirror `db.usercourseprogresses.countDocuments()` → 10; `$unwind items, status:'completed'` → 184; `learners.process.topic.ts:193-197`; phase-02 "Who owns what" (web owns detection).
- **Suggested fix:** Replace gate 7 with two unit assertions: `writeItemPosition`'s update document contains no `status`, `completedItems`, `progress` or `completedTopics` path; and the existing characterisation test for `wasCompleted`. Add a sentence to the Overview: no retroactive completion; optionally scope a one-off backfill (`timeSpent >= 0.8 × durationSeconds` once Phase 1 lands) as a decision for the plan owner.

## Finding 9: Parallel-phase file ownership and rollback are under-specified for the files that actually conflict
- **Severity:** Medium
- **Location:** Phase 4 Risk row "Phase 4 and Phase 5 both edit shared files"; Phase 5 Risk row "Phase 7 also edits `courses-routes.tsx`"; Phase 7 "Route placement"; Phase 2 step 2 ("additive … no migration")
- **Flaw:** (a) `scripts/check/sweep-routes.json` is a single JSON array and every locale file is a single object (`en.json` 853 lines): "append-only" edits by two branches both touch the closing bracket/last entry → textual merge conflict on every pair, not "Low". (b) Phase 7 may land before Phase 5 and mounts `about` as "a static child of the Phase 5 shell" that does not yet exist; the fallback ("Phase 5 absorbs it") makes Phase 5's scope depend on merge order. `feature-routes.test.ts` joins `prefix/path` and detects only literal duplicates (`:27-39`); it cannot detect the `about` vs `:itemId` ranking question the plan raises, so the cited gate does not gate that. (c) Rollback of Phase 2 after positions exist: old API code's `save()` in the mixed `$push`+`$set` case (Finding 4) rewrites the whole `items[]` from a hydrated document whose subdocument schema lacks `videoPositionSeconds`; whether Mongoose preserves unknown subdocument fields through that path is not asserted anywhere. If it does not, rolling the API back silently wipes every learner's position on their next `/track`. (d) Phase 4's compound index `{dueDate, status, deletedAt}` and Phase 7's `level` enum with `default: null` are fine to roll back, but Phase 7 gives no precedent in the repo for `enum` + `default: null` on a String path (grep found ObjectId/Date nulls only) — validate on the mirror as step 1 says, but write the assertion down.
- **Failure scenario:** Phase 4 and 5 merge within the same week → two conflict resolutions in seven locale files and the sweep JSON, one of which drops a key → `locale-completeness-gate.test.ts` fails on main. Phase 2 hotfix rollback → positions vanish for active learners without an error.
- **Evidence:** `ls apps/web/src/i18n/locales/` (7 files), `wc -l en.json` → 853; `feature-routes.test.ts:27-39`; `learners.process.topic.ts:35-45, 227-247`; phase-05 route tree; phase-07 "Route placement, and the collision to know about".
- **Suggested fix:** Give Phase 4 and Phase 5 separate sweep fixture files merged by the sweep script, or serialize the two merges explicitly in plan.md. Pin the order Phase 5 → Phase 7 (Phase 7 already depends on Phase 3's `outline-summary.ts`, so it is not truly independent of the Release 2 stack). Add a rollback test to Phase 2: write a position, then run the *pre-Phase-2* `processTopicProgress` against that document and assert the field survives; if it does not, Phase 2 needs a `strict: false` note on `ContentItemSchema` or a documented "no rollback after enable".
